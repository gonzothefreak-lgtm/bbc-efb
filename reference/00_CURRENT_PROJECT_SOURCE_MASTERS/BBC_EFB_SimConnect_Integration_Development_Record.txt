Version: 0.8 | Date: 2026-11-23 | Status: Migration freeze; R3.1 offline-validated source candidate; native live integration BLOCKED

PURPOSE
Living technical reference for simulator connectivity, aircraft-specific adapters, decisions, research, implementation and verification. Read alongside the Project Master Prompt, BBC EFB Project Development Record, current source and CHANGELOG. This document does not authorize coding or a build.

1. AGREED REQUIREMENTS
SIM-001 — Bidirectional architecture. Design the simulator interface for both reading telemetry and sending supported commands. Initial milestone is read-only; no command functionality should be enabled without a specific approved use case and safety design.
SIM-002 — Modular aircraft integration. Aircraft-specific modules (e.g., PMDG, Fenix) should be independently addable without coupling the core EFB to a particular aircraft. Interface methods, licensing, compatibility and availability require research.
SIM-003 — Separate simulator adapters from aircraft adapters. Simulator adapters manage platform connectivity; aircraft adapters enrich supported aircraft data and may use additional documented interfaces.
SIM-004 — Start with MSFS 2020; separately test MSFS 2024. Do not assume parity.
SIM-005 — Keep simulator connectivity isolated from UI modules. Prefer a shared connection manager, standardised telemetry/events, and module subscriptions.

2. PROPOSED ARCHITECTURE — NOT IMPLEMENTED OR APPROVED IN DETAIL
EFB modules (flight tracker, logbook, dispatch, future systems)
    <-> Simulator Integration Manager
        <-> Simulator adapter (initially MSFS SimConnect)
        <-> Aircraft-specific adapter (optional)
The manager would own connection state, telemetry distribution, reconnection, diagnostics, capability reporting and validated command dispatch. Modules should fail independently, and standard data should remain available if an add-on adapter is unavailable.

3. INITIAL TELEMETRY CANDIDATES
Position (latitude/longitude), altitude, indicated and ground speed, heading, vertical speed, on-ground status, engine state, fuel, aircraft identity and simulator connection state. Flight-phase, takeoff, touchdown, flight-time and logbook events may be derived. Landing rate, G-force and payware-specific data need explicit availability/accuracy checks.

4. FUTURE WRITE/COMMAND DESIGN
Provide a command abstraction but disable aircraft-changing operations initially. Future commands require explicit user-triggered intent where appropriate, supported simulator/aircraft capability checks, validation, timeout/error handling, logging and clear UI feedback. Do not assume all simulation variables are writable or all aircraft respond to standard events.

5. AIRCRAFT MODULE STRATEGY
Possible adapters: default/general aircraft, PMDG, Fenix, other third-party aircraft. Proposed: capability declaration, aircraft identification, independent enable/disable, fallback to standard telemetry, per-aircraft compatibility matrix. Open decision: bundled modules versus external plugin directory; external code loading requires versioning and security design.

6. PYTHON / SDK RESEARCH TO COMPLETE
Compare native Microsoft SimConnect SDK access against Python wrappers: supported APIs, Python and Windows compatibility, event/data subscription handling, thread model, error recovery, MSFS 2020/2024 compatibility, licensing, redistribution and PyInstaller packaging. Verify official SDK documentation and each aircraft vendor's published integration options before choosing a library.

11. APPROVED BASIC SIMCONNECT DESIGN REVIEW — QUESTIONS 1–15 (2026-11-17)
All decisions below are APPROVED DESIGN, not implemented or tested. Question 11 was withdrawn as redundant.
Q1 — Support local and network SimConnect in the architecture; implement local desktop connectivity first. Simulator frame-rate/frame-time impact must be minimised and measured.
Q2 — User-selectable automatic or manual connection mode; automatic is proposed default. Manual disconnect must suppress automatic reconnection until requested.
Q3 — Adaptive, consumer-driven telemetry: request only needed data, share subscriptions between modules, use appropriate rates and release/suspend unused requests. Avoid unnecessary definition churn.
Q4 — Consumer-driven background operation: minimising the main EFB must not stop data needed by logbook, stream overlays, plugins or other active consumers; suspend visual-only updates when unused.
Scope clarification — EFB is primarily read-only; do not implement general aircraft/system controls. Only consider commands if a verified vPilot-related workflow specifically requires them, subject to explicit approval and supported integration research. This supersedes the broader speculative write capability as an implementation goal.
Q5 — Detect disconnections, preserve recorded data, mark gaps and stale data, and recover according to automatic/manual mode; use controlled retry/backoff.
Q6 — Pause-aware telemetry; distinguish ordinary Pause and Active Pause, elapsed wall time, simulation time and flight time; test actual simulator behaviour.
Q7 — Automatic aircraft detection and matching plugin activation with user manual override; standard telemetry remains fallback.
Q8 — Aircraft plugin failure triggers safe deactivation, diagnostics and automatic fallback to standard SimConnect telemetry. Genuine crash isolation requires architecture/testing, not exception handling alone.
Q9 — Full offline EFB operation for features not requiring live simulator data.
Q10 — Lightweight built-in connection/performance diagnostics accessible from a menu; detailed SimConnect diagnostics in a dedicated Settings panel/menu, not the main flight workspace. Measure subscriptions, rates, data age and EFB overhead; simulator FPS impact requires controlled in-sim tests.
Q11 — Withdrawn: MSFS provides SimConnect server; EFB client connects under the Q2 mode. No separate server start or redundant service-start option.
Q12 — Track telemetry age and quality; mark live/stale/unavailable using data-specific thresholds; never present stale data as live.
Q13 — Structured local diagnostic logs by default, with optional detailed troubleshooting mode, file rotation/retention and performance safeguards. Time-limited debug mode is a recommendation, not a separate approved requirement.
Q14 — Persist local connection and diagnostics settings; multiple connection profiles reserved for a later phase.
Q15 — Graceful EFB shutdown: stop new requests, release subscriptions, close SimConnect, flush flight logs and terminate background services; bound shutdown waits to avoid indefinite hangs. Tray operation deferred.

12. PRIORITIES / IMPLEMENTATION BOUNDARIES
Initial scope: local MSFS 2020, read-only, demand-driven telemetry, reliable connection states, graceful recovery and shutdown. Network connections, MSFS 2024 and multiple profiles are future capabilities requiring separate verification. Plugin failures and telemetry quality must not silently corrupt logbook records or stream overlays. No source changes or live testing were authorised by this review.

SIMCONNECT TECHNICAL IMPLICATIONS / DESIGN REQUIREMENTS
- Maintain a single central subscription/distribution path where feasible;
  avoid duplicate requests by panels, logbook, overlays and aircraft plugins.
- Choose telemetry update cadence by consumer need and data criticality;
  avoid excessive polling, definition churn and unnecessary background work.
- When the window is minimised, suppress unused visual updates, but keep
  essential logging and other active background consumers supplied (Q4).
- Keep telemetry queues, retry state, diagnostic history and caches bounded;
  protect UI responsiveness and flight-log integrity under load.
- Instrument connection state, requested variables, active consumers,
  update rates, last received age, stale/unavailable counts, reconnect
  attempts and approximate EFB-side processing overhead. Diagnostic
  sampling itself must remain lightweight; detailed debug remains opt-in.
- Measure simulator FPS and frame-time impact with controlled in-sim tests,
  including frame-time spikes, not just average FPS. No impact is assumed.
- Maintain graceful disconnect/reconnect and bounded shutdown (Q5, Q15).

PROJECT-WIDE PROVISIONAL PERFORMANCE TARGETS (NOT SIMCONNECT-ONLY BUDGETS)
  EFB idle CPU: under 1% on reference test PC.
  EFB normal CPU: under 3% average on reference test PC.
  EFB RAM: under 300 MB initially.
  Minimized: CPU as close to idle as practical while preserving logging.
  Simulator: no consistently measurable FPS/frame-time degradation.
These are engineering goals, not benchmarks, guarantees or final pass/fail
criteria. Reference hardware and test methods remain to be agreed.

MAIN UI HANDOFF / DATA CONTRACTS

APPROVED SERVICE-LIKE CORE DIRECTION
- Black Box Core should behave as a logically self-contained shared-
  information service/subsystem, even if the initial implementation is
  in-process within the single-computer EFB. This does not authorise a
  Windows service, separate executable or local server.
- EFB pages/modules needing shared provider data should obtain it through
  documented, versioned Core consumer interfaces rather than directly from
  the simulator or provider implementation. Interfaces should support
  independently evolving consumer modules with compatible Core capabilities.
- Keep a centrally managed simulator connection/subscription path; do not
  introduce a second competing SimConnect manager. Additional providers,
  where approved, may have distinct legitimate provider-side connections.
- The Black Box Flight Recorder is a separate Core consumer, owned by
  Logbook Page Dev, not a universal persistence layer or mandatory gateway
  for other consumers. Failure in recording should not stop data delivery to
  healthy EFB modules. Recorder events, records and persistence remain
  Logbook-owned.
- Stable interfaces do NOT imply a selected transport, public SDK,
  separately updatable module binaries or permanent absence of Core changes.

APPROVED EXPANDABLE SUBSCRIPTIONS — DESIGN DETAILS TO WORK THROUGH
- New and existing consumers should request data as their needs evolve,
  and compatible requests should share source subscriptions where practical.
- Do not collect every available simulator variable just in case; preserve
  Q3/Q4 demand-driven activation, appropriate update rates, minimised
  essential-background behaviour and reasonable provider overhead.
- Research/decide later: request and release lifecycle; consumer registration;
  how overlapping data/rate needs are reconciled; quality/freshness and
  provenance exposure; source capability discovery; data-change/version
  compatibility; slow-consumer isolation; queue/back-pressure limits;
  disconnection/re-subscription behaviour; diagnostics and test criteria.
- These details are NOT yet an approved implementation specification.
  Actual variable mappings and Logbook flight-data needs remain candidates
  until verified and reviewed with Logbook Page Dev and Main.

APPROVED INDEPENDENT MODULE DEVELOPMENT
- Keep shared Core contracts separate from each module's own logic, UI,
  recording rules and storage decisions. Normal evolution of an existing
  page/module should not require redesigning the Core or unrelated modules.
- New underlying data capabilities may require controlled Core/adapter
  extensions, preserving compatible consumers where feasible.
- Main Development Chat retains approval of shared system boundaries,
  interface contracts, hosting/packaging and cross-workstream decisions.

EVALUATION ALTERNATIVES — ALL PACKAGE/IMPLEMENTATION CHOICES UNAPPROVED
A. Maintained existing Python SimConnect wrapper (FIRST to evaluate):
   Pros: less native callback/data-management code; faster initial work if
   SDK functions are covered. Risks: missing events/Client Data APIs,
   unmaintained wrappers, update lag, packaging issues, third-party licences.
   Example candidates mentioned in 23 Nov research: pysimconnect (Core
   reports a 0.3.0/15 Nov 2026 MIT beta release), simconnect-H (mentioned
   in Main's comparative discussion), and odwdinc/Python-SimConnect
   (Core reports AGPL-3.0 repository). These release and licence claims are
   RESEARCH REPORTS, not an approved or project-verified package inventory;
   resolve conflicting version listings against primary release metadata.
   Do not choose solely by publication recency. Particularly review the
   AGPL licence before any integration into distributable EFB software.
B. Direct Python bindings to the official native SimConnect SDK (FALLBACK):
   Pros: full control over exposed API surface and binding lifecycle;
   no dependency on a third-party Python wrapper. Risks: callback/message
   dispatch, native structs and bitness, error handling, compatibility,
   packaging, maintenance and greater implementation effort.
C. Small native C++/C# bridge (OPTIONAL RESEARCH ALTERNATIVE):
   More languages, build artifacts, interop/process considerations;
   not selected and not a requirement for C0.1.
D. FSUIPC7 (SEPARATE SECONDARY/ALTERNATIVE SIMULATOR SOURCE CANDIDATE):
   Not a SimConnect Python binding. Existing Project Sources preserve it
   as optional; owner explicitly corrected any suggestion it was excluded.
   SimConnect is investigated FIRST. No decision to include, reject or
   require FSUIPC7 in NEW C0.1; assess only if a concrete data/compatibility
   benefit emerges, with licensing and dependency overhead reviewed.
