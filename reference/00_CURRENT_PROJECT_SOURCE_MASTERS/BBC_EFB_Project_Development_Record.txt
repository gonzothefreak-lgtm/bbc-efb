1. HOW THE PROJECT STARTED AND EVOLVED
--------------------------------------
The initial idea was an electronic flight logbook for flight simulation and
VATSIM. The scope grew into a standalone, integrated Windows Electronic Flight
Bag (EFB) and pilot workstation, intended to reduce switching between multiple
programs and browser windows during VATSIM operations. The logbook remains a
major planned feature, but is now one of three top-level workspaces.

The project owner is a real-world pilot, makes aviation/UX decisions and is
learning software development. ChatGPT assists with architecture, research,
interface design, code, troubleshooting and documentation. The project owner
has final approval over design changes and when code/builds are executed.

2. PRODUCT VISION AND DESIGN PRINCIPLES
---------------------------------------
- Windows 10/11 standalone desktop application, initially focused on VATSIM.
- Professional, uncluttered, aviation-oriented interface.
- Local-first, modular and maintainable; integrations are optional modules.
- Reliable during flight, with clear connection states and graceful failures.
- Configurable workspace: dock, resize, hide/reopen, move and eventually pop
  panels into separate Windows windows for multiple monitors.
- Avoid unsupported third-party embedding and respect API/licensing limits.
- Design and test incrementally; preserve previous working builds.
- Android companion support and home-cockpit/multi-PC ideas are long-term only.

3. MAIN APPLICATION WORKSPACES — AGREED CONCEPT
-----------------------------------------------
A. DISPATCH
   Preflight planning and preparation, including proposed SimBrief dispatch,
   operational flight plan (OFP), weather and navigation resources.

B. IN-FLIGHT
   The main modular pilot workspace. Candidate panels include vPilot,
   VATSIM radar, SimBrief OFP, weather, Hoppie ACARS/CPDLC and charts.
   A Modules launcher is to remain visible on the RIGHT side of the window,
   including while the window is resized. The centre workspace must adapt to
   available width, not push the launcher off screen.

C. LOGBOOK
   Original core idea: eventual automatic flight logging, history,
   statistics, flight times and possible landing-rate recording.

Top-level Dispatch / In-Flight / Logbook navigation is used in current concepts.
The final navigation placement is not permanently locked down.

13. SIMULATOR PERFORMANCE AND LIGHTWEIGHT OPERATION — 17 NOVEMBER 2026
---------------------------------------------------------------------
Status: Project owner-approved design priority; not implemented or benchmarked.

Core principle: The simulator receives resource priority. The EFB should
consume only the resources needed to deliver its active functions.

Design requirements:
- Use demand-driven SimConnect subscriptions and share telemetry among
  consumers; avoid redundant or unnecessarily frequent polling.
- Keep UI redraws, animations, background rendering and GPU use modest.
- When minimised, reduce visual work while continuing essential background
  services such as flight logging.
- Inactive optional modules should not consume substantial resources.
- Bound telemetry buffers, diagnostic histories and caches.
- Monitor CPU, RAM, GPU, telemetry traffic, simulator FPS and frame times;
  test for spikes and stutters as well as averages.
- Add a Performance Diagnostics area under Settings (UI design proposal,
  details to be reviewed).

Provisional performance goals, subject to representative Windows/MSFS testing:
  Idle EFB CPU: under 1% on reference test PC.
  Normal EFB CPU: under 3% average on reference test PC.
  RAM: under 300 MB initially.
  Minimized: as close to idle CPU activity as practical.
  Simulator: no consistently measurable FPS/frame-time degradation.
These are engineering targets, NOT guarantees, benchmarks or acceptance
results. Reference hardware, test methodology and thresholds require review.
Reliability and flight-log integrity take priority over arbitrary limits.

Cross-chat handoff: Dedicated SimConnect research chat should assess
subscription cadence, shared data distribution, idle/minimised behaviour,
reconnect cost, diagnostics and telemetry overhead. No SimConnect technical
design has been changed here without that workstream's review.

Also approved: bottom SimConnect indicator should be clickable to open
Settings > SimConnect > Connection Diagnostics; hover should show connection
status, simulator identity and data freshness when available.

No application source changes or new builds authorised by these decisions.

17. CLEAN DEVELOPMENT / COMPLETE RELEASE / PERFORMANCE REGRESSION POLICY
----------------------------------------------------------------------
Status: OWNER-APPROVED project-wide development and release policy, recorded
18 November 2026. Implementation, automated checks and benchmarks do not yet
exist. This supplements sections 5, 9, 11 and 13 without replacing them.

PURPOSE
Avoid accumulated ad-hoc patches, redundant services, brittle code and
resource-intensive integrations as additional EFB functions are developed.
Each version should remain one coherent, modular and maintainable application.

MANDATORY DEVELOPMENT PRACTICES FOR FUTURE AUTHORISED BUILDS
1. Before changes, review the WHOLE current-project source structure,
   dependencies, interaction boundaries, existing functionality, diagnostics
   and performance implications of the proposed features.
2. Design new features into appropriate existing modules or refactor affected
   modules. Do not keep stacking workarounds, duplicate services, dead code,
   obsolete alternate implementations or one-off patches over previous fixes.
3. Reuse well-designed, verified components where sensible. "Fresh build"
   means fully reviewed, coherent source and CLEANLY regenerated build output,
   NOT gratuitously rewriting every functioning module from zero. If current
   architecture is unsuitable, propose a deliberate refactor for approval.
4. Deliver a COMPLETE, independently buildable source set for the ENTIRE EFB
   for each release, with clear dependency versions, build procedure and
   build/version identity; no partial snippets, accumulated patch instructions
   or dependence on earlier release ZIPs to reconstruct the current version.
5. Build each release from a clean build/output directory, not from stale
   compiled artefacts. Archive previous working releases for rollback.
6. Maintain a new-project CHANGELOG from authorised C0.1 onwards: changed
   components, approved functionality, fixes, refactors, known limitations,
   measured results and actual test status. Do not import the old project's
   C0.1-C0.3 release history as current implementation.
7. Review maintainability before delivery: clear module responsibilities,
   limited coupling, shared services, failure isolation, bounded workers,
   safe shutdown, sensible logging, no unnecessary dependencies, and no
   disabled/placeholder module pretending to operate.
8. Regression-test previously working functions when new functions are added.
   Record which automated or manual tests actually ran, on which environment;
   anything untested must be clearly identified. A clean rebuild alone does
   not demonstrate clean architecture, correctness or performance.
9. Any major architectural change requires discussion and owner approval.
   No application coding or builds proceed without explicit authorisation.

PERFORMANCE REGRESSION STANDARD — SIMULATOR RECEIVES PRIORITY
- New functionality must be assessed for idle and flight CPU/RAM/GPU cost,
  UI responsiveness, SimConnect traffic, disk/logging overhead, simulator FPS
  and especially frame-time spikes or stutters. Do not assume that adding
  features is allowed to degrade simulator performance unchecked.
- Share demand-driven telemetry subscriptions. Do not create redundant
  SimConnect connections/polling loops or refresh inactive visual modules
  unnecessarily. When minimised, reduce visual workload but maintain any
  essential active logging/background consumers.
- Use bounded queues, data buffers, caches, logs, retries and diagnostic
  history. Prevent low-priority diagnostic/render work from delaying reliable
  flight-log recording, cleanup or simulator operation.
- Establish a reproducible simulator-only reference, then compare each new
  release with the preceding verified release under representative, comparable
  MSFS 2020 scenarios and the same reference PC/settings when possible.
  Record CPU/RAM/GPU, overall FPS, frame-time distributions/spikes and test
  conditions. Separately verify MSFS 2024 when its support is attempted.
- Investigate unexplained performance regressions before declaring release
  readiness. Where real Windows/MSFS measurements cannot be run, record the
  gap as NOT TESTED rather than claiming targets were achieved.
- Section 13's provisional project-wide goals remain UNDER 1% idle CPU,
  UNDER 3% average normal CPU, UNDER 300 MB RAM, and no consistently
  measurable simulator FPS/frame-time degradation. Hardware/test thresholds
  have not been established; these are NOT guarantees or achieved results.
- Safety, reliable operation and flight-log integrity take precedence over
  arbitrary numerical targets. Baselines and pass/fail criteria need separate
  owner review before being enforced as release gates.

CROSS-CHAT COORDINATION

- SimConnect Integration Chat owns the technical feasibility, telemetry

20. BLACK BOX CORE / FLIGHT RECORDER / FUTURE NETWORK ARCHITECTURE — 22 NOVEMBER 2026
-------------------------------------------------------------------------------------
Status: Approved HIGH-LEVEL architectural direction from the Main Development
Chat, plus explicitly identified owner-directed PROPOSALS from the separate
22 November handoff. Not a technology selection, interface specification,
implementation plan approval, source-code authorisation or test result.

ORIGIN AND DESIGN INTENT
- The project owner identifies Black Box Core (BBC) as the overall EFB's
  central SHARED INFORMATION SYSTEM, with a recognisable Black Box Flight
  Recorder as a DISTINCT consumer/component. The name also reflects The
  Black Box Club. It does not rename the overall EFB product.
- Both are logical responsibilities: they need not be separate executables,
  Windows services, processes, servers or mandatory background workers.
- Black Box Core should expose documented, stable, versioned access contracts
  to the EFB and future authorised consumers. Internal Core improvements
  should not require updates to unaffected consumers while compatibility is
  preserved. Versioning alone does not make independent binary upgrades safe
  or feasible; packaging and compatibility need separate research.
- The Core can coordinate supported simulator, VATSIM and future integration
  data through modular source-specific services/adapters. It must NOT become
  a monolithic recorder, unbounded broker or a second competing SimConnect
  connection/distribution manager.

APPROVED BOUNDARIES / EXISTING REQUIREMENTS PRESERVED
- SimConnect Integration continues to own the simulator-facing connection,
  shared demand-driven subscriptions, telemetry freshness and recovery. It
