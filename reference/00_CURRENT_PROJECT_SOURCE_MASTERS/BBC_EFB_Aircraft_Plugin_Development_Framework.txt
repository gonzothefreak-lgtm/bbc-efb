BBC INTEGRATED EFB — AIRCRAFT ADD-ON PLUGIN DEVELOPMENT FRAMEWORK
Version: 0.5 | Date: 2026-11-23 | Status: Proposed design / research — PMDG 737 research focus; no adapter selected

PURPOSE
Define a future community-extensible aircraft integration mechanism for the BBC Integrated EFB. Users and aircraft developers may eventually install aircraft-specific adapters in an external folder without rebuilding the Windows application. This is a design record, not an implemented plugin API, SDK, or authorization to code.

RELATIONSHIP TO OTHER RECORDS
Read alongside the Project Master Prompt, BBC EFB Project Development Record, SimConnect Integration Development Record, current source files and CHANGELOG. The simulator connection manager should own platform connections. Aircraft plugins should use a controlled, documented host interface rather than independently opening conflicting simulator connections where avoidable.

1. DESIGN GOALS
PLUG-001 — Support optional user-installed aircraft integration modules from a directory alongside the packaged executable.
PLUG-002 — Keep simulator adapters (e.g. MSFS SimConnect) separate from aircraft-specific adapters (e.g. PMDG or Fenix).
PLUG-003 — Provide a versioned host/plugin contract and capability declarations; preserve standard simulator telemetry if an aircraft plugin is absent or fails.
PLUG-004 — Make read-only telemetry the initial plugin capability. Design for guarded future command/write requests, but do not enable by default.
PLUG-005 — Make module installation, enable/disable, diagnostics and compatibility understandable to non-developer users.
PLUG-006 — Do not execute arbitrary downloaded Python code silently. Security and trust policy must be designed before external plugins are enabled.

Folder names and files are suggestions. Bundled and external plugins may require separate directories and trust rules. The existing local-first storage approach (JSON, JSONL, TXT, CSV) remains unchanged.

3. PROPOSED MANIFEST CONTRACT (FIELDS TO FINALISE)
Plugin ID, human-readable name, author, version, plugin API version, supported simulator(s), aircraft identity/matching criteria, declared telemetry capabilities, declared command capabilities, required dependencies, permissions, source/support URL, and optional compatibility notes. Manifest metadata is not proof that a plugin is safe or compatible. No concrete schema is approved yet.

4. HOST / PLUGIN INTERFACE (CONCEPTUAL)
Host: provides connection state, standard telemetry subscription, event delivery, structured diagnostics and a guarded command gateway.
Plugin: identifies supported aircraft, translates aircraft-specific data to canonical EFB fields, advertises capabilities, handles connection changes and shuts down cleanly.
Prefer normalized units, timestamps, data-source labels, quality/availability flags, and explicit handling of missing/stale values. Do not overwrite standard telemetry without provenance or precedence rules.

5. DETECTION AND FALLBACK
Proposed sequence: detect simulator and aircraft; compare against declared match rules; identify compatible enabled plugins; resolve conflicts deterministically; activate selected plugin; fall back to generic SimConnect data when unsupported or unhealthy. Aircraft identification and matching must be tested against actual aircraft packages and variants.

6. SAFETY AND TRUST
Python modules execute arbitrary code with the application's user privileges if imported in-process. A folder-based loader does not create a sandbox. Consider an explicit installation/enable workflow, signed or verified distributions where practical, source review, permissions disclosure, user confirmation and process isolation for untrusted code. Process isolation improves fault containment but is not by itself a full security sandbox. Do not promise crash isolation for in-process Python plugins. Commands affecting aircraft state require separate opt-in and validation.

7. COMPATIBILITY AND PACKAGING RESEARCH
Evaluate Python interpreter/runtime availability for user-authored .py modules in a PyInstaller-frozen EXE; third-party dependency installation and isolation; plugin API semantic versioning; MSFS 2020 versus 2024 differences; Windows 10/11; and licensing/redistribution restrictions. A standalone EXE does not automatically guarantee external Python plugins and dependencies can be loaded. Do not choose an implementation until these constraints are tested.

8. AIRCRAFT-SPECIFIC INTEGRATION RESEARCH
Investigate documented PMDG, Fenix, iniBuilds and other add-on interfaces independently. Standard SimConnect variables/events may be insufficient for custom systems. Do not assume vendor APIs, SDKs, data channels or redistribution permissions exist without verification. Prefer supported official methods and obtain developer permission when required.

9. PROPOSED USER EXPERIENCE
Settings > Aircraft Plugins: list detected modules, aircraft compatibility, source/author, version, enabled state, requested capabilities, status and errors. Offer a safe way to install/update/remove plugins; never silently auto-execute newly copied scripts. Maintain logs and a recovery mode that disables problematic plugins.

11. OPEN DECISIONS

- How should external dependencies be distributed and verified?
- How are plugins approved/trusted, updated and revoked?
- How should simultaneous plugins and aircraft variants be prioritized?
- What is the minimum supported plugin API version and upgrade policy?
- Which aircraft integration is the first official reference implementation?

12. APPROVED AIRCRAFT PLUGIN BEHAVIOUR (2026-11-17)
The following decisions are approved in the basic SimConnect review, but NOT implemented or tested:
- Automatic aircraft detection and plugin matching, with a manual override for aircraft variants or ambiguous matches (Q7).
- Automatic fallback to generic/standard SimConnect telemetry if a plugin is missing, disabled or fails (Q8). Mark plugin-only values unavailable/stale rather than pretending they are live.
- Consumer-driven telemetry subscriptions shared through the central manager, including background consumers such as stream overlays while the main EFB is minimised (Q3–Q4).
- Plugin error diagnostics in the dedicated Settings diagnostics panel and structured local logs, with optional detailed troubleshooting (Q10, Q13).
- Graceful plugin deactivation and shutdown; a faulty plugin must not indefinitely block EFB exit (Q15). This requires isolation/timeouts to be designed and tested.
- Read-only telemetry is the intended aircraft plugin scope. Do not add general simulator control capabilities. Any vPilot-related command exception requires separate evidence, design and approval.

PRIORITISATION
- The owner requested that PMDG be the FIRST AND ONLY manufacturer for
  initial aircraft-specific feasibility work, focused on the PMDG 737.
  Fenix, iniBuilds and other vendor adapters are deferred for later
  investigation. Future extensibility and detection/fallback still apply.
- Support of standard SimConnect telemetry in third-party aircraft must be
  evaluated independently of any vendor SDK. Do not assume all add-on
  aircraft report the same standard values, and do not make PMDG mandatory
  for the first logged flight or C0.1 release.
- The PMDG 737 NG3 SDK header found in secondary research suggests a
  SimConnect Client Data channel named PMDG_NG3_Data and a configuration
  switch EnableDataBroadcast=1. These exact names are NOT verified against
  official installed PMDG products, supported 737 variants, permissions or
  simulator versions; no silent settings or broadcast changes authorised.

TARGETED PMDG RESEARCH QUESTIONS FOR BLACK BOX CORE DEV
- Identify exact product family/build and officially supplied, licensed SDK.
- Verify whether existing SimConnect session can subscribe to supported
  read-only Client Data without duplicate connections/workers, and whether
  client data are enabled or require explicit user configuration.
- Check whether any documented PMDG field adds meaningful value to the
  Recorder's existing flight detection, touchdown, aircraft identity,
  parking/engine context, weight or operational requirements. Do not invent
  landing-rate, cargo categories or aircraft system fields.
- Assess data type/unit, timestamp/freshness and advertised capabilities,
  update rates, plugin failure modes and safe generic fallback.
- Check vendor licence/SDK redistribution, security trust, Windows/MSFS
  version compatibility, integration maintenance and bounded overhead.
- Make no implementation or C0.1 inclusion recommendation until evidence
  shows an actual benefit beyond standard SimConnect and the owner reviews it.
