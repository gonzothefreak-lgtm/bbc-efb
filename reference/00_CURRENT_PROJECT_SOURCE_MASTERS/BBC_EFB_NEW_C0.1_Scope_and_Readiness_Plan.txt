1. PROJECT BASELINE / NON-NEGOTIABLE APPROVED DESIGN
----------------------------------------------------
- NEW project: NO active source code, application build, SimConnect implementation, Windows/MSFS validation or simulator performance baseline exists. Old C0.1–C0.3 are history, not an implementation baseline.
- First future owner-authorised version is NEW C0.1. EVERY authorised concept/release build contains the established Dispatch, In-Flight and Logbook Sections and accessible Settings, even when some functions are explicitly labelled placeholders.
- Approved dark, slim, borderless Windows 10/11 styling; the In-Flight right Modules launcher must remain accessible during resizing. Same approved visual language across Sections. The permanent bottom footer shows separate SimConnect and Flight Logging indicators with distinct ownership/actions.
- Black Box Core: logical shared information gateway, one consumer-driven, centrally managed read-only MSFS 2020 SimConnect path, stable internal contracts and bounded processing. Not a mandatory separate process, server or LAN endpoint. MSFS 2024 remains for separate validation.
- Black Box Flight Recorder (Logbook-owned): consumes Core observations; defines actual flights/events, logging state, record lifecycle, provenance, persistence, corrections, interruptions and pilot-facing Logbook UI.
- Simulator receives performance priority. Local-first JSON/JSONL/TXT/CSV preferred; SQLite, mandatory cloud, unapproved external integration, network server and general aircraft controls not authorised. Fresh release = coherent complete independently buildable EFB tree; no overlapping ad hoc patches.

-------------------------------------------------
APPROVED TARGET / PRIORITY: Freeze speculative new-feature design and focus on a FULL EFB CONCEPT with genuinely usable Logbook and LIVE read-only MSFS 2020 SimConnect-backed automatic Flight Logging (with manual override in the approved UX). The intended release must not be a Logbook-only app or fake working telemetry demo.
NOT YET APPROVED: exact minimum flight fields/event rules, screen subset to be fully functional, specific aircraft range, source SDK/library, full UI customisation in C0.1, platform packages, acceptance criteria, individual intermediate build releases or authorisation to code/test/build.
Approved UI visuals (Logbook Q1–Q14) remain the design reference. Not every illustrated advanced interaction/metric is automatically a C0.1 deliverable.

3. PROPOSED FIRST IMPLEMENTATION SUBSET (OWNER MUST APPROVE)
-------------------------------------------------------------
A. SHELL / APPLICATION-WIDE
- Working slim borderless window: launch, navigation, Settings, resize/maximise/restore/minimise/close; ensure Modules launcher never disappears. Retain both footer indicators even in narrow windows.
- Dispatch: full themed section with realistic CLEARLY NON-LIVE placeholders for unimplemented services.
- In-Flight: full themed section with accessible anchored Modules launcher and realistic CLEARLY NON-LIVE modules; working shared shell interactions. Candidate Aircraft Status information may be live only where actually implemented and verified.
- Settings: accessible SimConnect connection controls and diagnostics; Flight Logging & Privacy explanation accurate to actual behaviour; Logbook view preferences and Data Management entry where selected. Actions not implemented should be labelled unavailable.
- Shared customisable panel system is APPROVED in design for Logbook/In-Flight, but whether its full drag/resize/preset functionality ships in C0.1 is OPEN. Do not let advanced panel docking block reliable flight logs.
B. LOCAL LOGBOOK
- Working manual flight creation with four approved required fields: aircraft type, From, To and flight date; remaining fields optional, honest unknown values, local durable save/read.
- A practical usable Flight History and in-EFB Flight Details overlay; search/filter/edit and original-value/correction provenance to the extent specifically approved for the milestone. Existing approved Table/Cards/Combined modes remain design intent; which modes work in the first build is OPEN.
- A Logbook Dashboard, Recorder Management and Statistics page present in the shell; only actual implemented summaries/actions are interactive, the rest explicitly placeholders.
- Confirmed diversions appear only when pilot-confirmed; optional crew/PAX/baggage/freight/payload may be manually entered if included, never fabricated from SimConnect station data.
C. LIVE MSFS 2020 / CORE / RECORDER
- One centrally managed read-only simulator source; honest connected/disconnected/reconnecting/quality state and traceable, bounded observations.
- Essential flight state and timing signals support a MINIMUM credible auto-start, takeoff, landing and completion workflow subject to Logbook event-rule approval. Manual override and confirmation before active Stop Logging.
- Save a genuine local flight record and expose Recorder health/active state independently of simulator connection. Preserve interruptions honestly; no silent gaps or invented landing-rate/ICAO information.
- PMDG 737 is only an INITIAL vendor-feasibility research target; its adapter is not committed for C0.1. Generic SimConnect logging should remain usable without it. FSUIPC7 is an optional secondary/alternative, not required or rejected.

5. PROPOSED C0.1 VERIFICATION / ACCEPTANCE MATRIX (UNAPPROVED)
-------------------------------------------------------------
Each test must be performed and recorded on actual stated Windows and MSFS hardware/software before claiming PASS. Evidence status today: NOT TESTED for every item.
- Windows: launch, resize narrow/wide, minimise, restore, taskbar-safe maximise, close; accessible navigation, Settings, right Modules launcher and dual footer.
- Offline: show honest simulator-disconnected status; manual log entry, saved history, corrections and relevant settings continue without simulator.
- SimConnect: genuine MSFS 2020 standard aircraft connect, identified source, appropriate units, connection state, shared demand-driven subscriptions; no raw mock telemetry represented as live.
- Recorder: one approved normal flight scenario with observable start, takeoff, touchdown, completion, manual start/stop override and durable saved record; data gaps exposed and source preserved.
- Time/edge cases: ordinary Pause, Active Pause, sim-rate changes, UTC midnight, touch-and-go/circuits and multi-leg cases must either meet explicitly approved behaviour or be visibly classed as unsupported/incomplete (no invented results).
- Resilience: simulator not running, delayed launch, disconnect, reconnect, simulator/aircraft reload, minimised recording, application shutdown/crash and safe incomplete-log recovery. Record what was actually tested.
- Data: observed vs derived vs pilot-entered/imported origin; missing fields, original values/edits, incomplete payload/landing-rate labelling, preservation of imported/manual records without bogus native gaps.
- Performance: repeatable simulator-only baseline vs EFB active/idle/minimised; CPU, RAM, GPU, disk, connection requests, simulator average FPS and especially frame-time distributions/spikes. Historical under 1% idle CPU, under 3% average CPU and under 300 MB RAM remain PROVISIONAL, not a claimed gate or achieved result.
- Packaging: complete source tree, pinned reviewed dependencies, PyInstaller/SDK redistribution research, clean build, instructions, release identity/changelog, limitations and actual tests/untested items.

8. CURRENT OWNER-APPROVED C0.1 ARCHITECTURE AND FUNCTIONAL SCOPE — 23 NOVEMBER 2026 (v0.2)
--------------------------------------------------------------------------------------------------
The decisions below were made AFTER the original v0.1 planning draft. They
are authoritative C0.1 directions when this updated Source is confirmed by
owner; they supersede older v0.1 'not approved' snapshots only as specified.
They do NOT authorise the next full EFB build or Windows/MSFS tests.

MAIN / UI FRAMEWORK AND RUNTIME
- Python + PySide6 / Qt Widgets selected for UI direction; specific version,
  Windows/licensing/packaging/performance evidence still outstanding.
- NEW C0.1: modular, ONE PROCESS, responsibility-based packages under an
  independent buildable full-EFB source tree; in-process versioned Core
  consumer interfaces and event notifications. Core and Flight Recorder
  remain independent logical components, not a shared monolith.
- NEW C0.2+: the owner's intended architecture has separate EFB UI, Core
  and Recorder processes, with coordinated IPC and start/stop supervision.
  Migration complexity, frame-time/CPU costs and reliability require review.
- UI load on demand; initial Section Dispatch. Essential Recorder/Core
  services can continue with other Sections open or the EFB minimised.
- HYBRID ADAPTIVE layout: reflow when practical, protect min usable widths,
  scroll as needed; right-side Modules launcher and dual footer always
  accessible. C0.1 BASIC saved layout/display/visibility preferences;
  C0.2+ FULL approved drag/resize/dock/customisation implementation.
- Active Flight Logging on app close -> Cancel or Save & Exit; preserve
  incomplete record, never silently convert to completed flight.

LOCAL FILES / DISTRIBUTION
- Pilot must choose a writable data directory on FIRST LAUNCH. Documents,
  a dedicated C: path or a custom folder are allowed, not a hidden mandatory
  AppData records folder. Treat OneDrive Documents redirection and root-path
  permission issues honestly. All actual flight records remain accessible.
- Component-owned records/configuration, shared safe file utilities and
  exclusive record write ownership. Per-record format, atomic update/recovery,
  migration and multi-process concurrency remain implementation decisions.
- NEW C0.1 distribution: PORTABLE ZIP with whole independently buildable
  application source and clear Windows launch/build instructions. No
  installer until separately reviewed.

OWNER-APPROVED OPTION B — FULL LOGBOOK FUNCTIONAL C0.1 TARGET
- Implement the EXISTING APPROVED Logbook experience (Q1–Q14), not a
  Recorder-only or deliberately reduced Logbook. Present Dashboard, full
  Flight History Table/Cards/Combined, Flight Details overlay and tabs,
  manual/native-record editing with correction/provenance, Recorder
  Management, Statistics/operational summaries, and appropriate Settings,
  exports and separate restorable backup controls as functionality permits.
- Real MSFS 2020 read-only SimConnect is required for native automatic
  Flight Logging. No fabricated flight details, ICAOs, landing rates,
  payload values, or unsupported G-force. Conditional metrics must honestly
  show unavailable/unknown or require proper pilot confirmation.
- Advanced shared layout drag/dock/customisation is already deferred to
  C0.2+ by owner decision. Likewise owner has PARKED aircraft/add-on plugins
  and user-installable developer modules until a separate discussion;
  'full Logbook' DOES NOT automatically reinstate speculative freight
  assignment/manifests, cloud integrations, extra aircraft adapters or
  high-rate black-box analysis not previously approved.
- Flight Recorder first/last event logic, actual timing and pause/circuit/
  multi-sector handling, error recovery, exact file schema, import formats
  and acceptance evidence remain individually unapproved. Logbook Dev owns
  recorder semantics, Core Dev owns feasibility, Main approves integration.
