PROJECT CHAT ROUTING — OWNER-APPROVED RULE (18 NOVEMBER 2026)
-------------------------------------------------------------
The Main Development Chat is the project-wide coordination hub. Every
existing and future specialist chat should help keep substantive decisions
and design work in the correct workstream, even if the owner accidentally
raises a topic in another chat.

Routing by current ownership:
- Main Development Chat: application architecture, whole-EFB UI shell,
  framework and environment selection, cross-chat coordination, shared
  policies, release/build planning and topics without an active owner.
- Black Box Core Dev: simulator connectivity, telemetry feasibility,
  subscription cadence, data freshness, simulator connection/performance
  diagnostics and optional aircraft-adapter technical research.
- Logbook Page Dev (ACTIVE): Logbook-specific user experience, flight
  recording workflow, record schema, history and statistics; cross-workstream
  architecture and shared storage policies remain with Main.
- As new chats are owner-confirmed and registered, use their approved scopes
  for routing; never guess that an unregistered chat exists.

Operating procedure for any receiving chat:
1. Recognise when a substantive request is outside the chat's registered
   responsibility, and briefly explain which chat owns it.
2. Gently suggest continuing in the correct ACTIVE chat. If cross-cutting,
   unclear or unassigned, use Main Development Chat as the safe default.
3. Supply a short, copy-ready handoff with the request, relevant approved
   constraints, decision status, destination and pending questions. Don't
   require the owner to remember or reconstruct context.
4. Keep simple related questions in context when useful, and always
   honour the project-wide "catch up on project" command in the receiving
   chat; avoid extended out-of-scope design, duplicate ownership or silently
   approving changes.
   If the owner intentionally keeps discussing the issue here, identify the
   formal owner and document a handoff for any consequential decisions.
5. Never imply that messages, ownership, approvals or documents have been
   automatically transferred to another chat. Project Sources only change
   after the usual complete-replacement and owner-confirmation workflow.
6. Be friendly and nonjudgmental: this is a coordination safeguard, not a
   reason to scold the owner for using the wrong conversation.

A concise version of this rule should also appear in the shared Project
Instructions so every newly created chat receives it at startup. This
register is the detailed routing reference; the Main Development Chat owns
maintenance and cross-workstream oversight. No coding/builds authorised.

LOCAL COMMUNICATION AND FUTURE NETWORKING
- C0.1 remains a single-computer, local-first application with the complete
  EFB shell and intended SimConnect-backed Logbook. A lightweight in-process
  interface may be sufficient; separate process, native Windows IPC and
  localhost transport are UNSELECTED implementation alternatives.
- Black Box Core is the FUTURE architectural home for optional network
  hosting and client-facing shared-data APIs. These are not C0.1 features.
